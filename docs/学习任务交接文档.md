## 2. 全局固定规则（硬性约束）

### 2.1 内容深度分级（L1/L2/L3）

| 层级 | 定义 | 检验标准 | 占比 |
|:---:|------|------|:---:|
| **L3** | 面试深度 | 能手写核心逻辑、能答连环追问、能讲清底层原理 | ~20% |
| **L2** | 项目深度 | 能正确使用、能排查、能讲设计决策 | ~50% |
| **L1** | 认知深度 | 知道是什么、解决什么问题、和同类技术的区别 | ~30% |

- 每个知识点必须标注 L1/L2/L3；
- L3 只给核心项（Agent 线的 RAG/LangChain、Python、MySQL 索引事务、Redis）；
- Java 辅线按"A 方案"降级：Spring Boot 到"会写会用"，**不深挖容器启动流程/代理源码**。

### 2.2 时间规划规范

**周计划结构**：7 天为一周（标起止日期+星期）；特殊时段做"专项计划"（9 天左右，命名加 `WeekN-` 前缀）；纯 Agent 阶段不双线交替。

**时间分配**：**练习时间 ≥ 学习时间**；参考配比 = 学新 1h + 动手 1h + 练习 3h + 默写 0.5h（共 5.5h）；强度按实际递减（暑期 8.5h → 开学 6h → 学期中 5.5h）。

**诚实时间账**（禁止假账）：
```
日历天 − 休息日 = 实质学习天
实质学习天 = 内容天 + 机动天
主线小时 = 实质学习天 × 该段日强度
```
装不下就**显式指出缺口**并指定买单方（不得隐去）。

### 2.3 评估规则

- **判断合理性**：时间账是否闭合；完成率趋势（连续低于目标 → 结构性高估，应下调内容量而非要求加倍努力）；前后周知识点衔接性。
- **识别漏洞**：里程碑项目是否被欠账挤掉；是否存在"输入够、输出不足"（用户表述："感觉都会了但差点东西"）；是否存在"虚假熟悉感"（曾让 AI 代写 → 眼熟 ≠ 会写）；缺口是否在扩大。
- **改进建议**：必须给**具体可执行动作**，不是原则性建议。已验证有效的手段：
  1. **三档练习法**（照抄档 → 半开卷档 → 闭卷档）
  2. **每天 1h 重写时段**
  3. **成果前置**（可演示的产出排专属日，不许被挤掉）
  4. **产出视角**替代知识地图（"手上有什么 → 本周多出什么" + 每天一句"这东西通向哪"）
  5. **降环境复杂度**（给零依赖兜底方案）

### 2.4 回答取舍原则

- 底层原理 + 实操并重：既讲"为什么"（原理、面试追问点），也给"怎么写"（可运行代码）；
- 中文输出；代码/标识符/路径/命令/术语保持原文不翻译。

### 2.5 禁止行为

- ❌ 不得随意更换输出模板（章节结构、表格列固定）；
- ❌ 不得擅自增减计划维度；
- ❌ 不得简化关键细节（关键代码必须完整可运行；面试问答必须含追问）；
- ❌ 不得做假时间账、不得隐去缺口；
- ❌ 不得因进度落后擅自修改总路线文档的排期（调整只写进执行表）；
- ❌ **不得只给"模糊方向"**（详见 2.6）。

### 2.6 详细度硬性要求（v2 新增，最重要）

> 背景：用户曾明确反馈"你给的只是大致方向 + 英文文档看不懂 + 我得东找西找，做完心里没底"。**从此所有产出必须达到下述详细度。**

**（1）周执行表的每一天，必须包含**：
1. **今日目标**（一句话）+ **完成标准**（可自检的 2-3 条）
2. **时间块拆解**（上午学概念 / 上午动手 / 下午练习 / 晚上默写，各写清时长）
3. 每个时间块写清：**读哪个文件的哪一节** + 重点搞懂什么 + ✅ 自检问题
4. 环境/操作类内容用**三列操作表**：`做什么 ｜ 预期看到 ｜ 卡住怎么办`
5. 练习清单用**三档法**（照抄 → 半开卷 → 闭卷），每条写清做什么 + 验证标准
6. **资源行**：`> **📚 资源**：…`（见 2.7）
7. 标注"卡住 → 查知识点总结的哪一节"

**（2）知识点总结必须包含 9 节**（见 3.2）。

**（3）禁止出现**：
- 只有"学 X + 练 Y"这种笼统描述；
- 只给英文官方文档链接（不给中文入口）；
- 只说"阅读文档"而不指明读哪一节；
- 操作性步骤没有"预期结果"。

### 2.7 资源选取原则（v2 新增）

| 优先级 | 类型 | 写法 |
|:--:|------|------|
| 1 | **B站搜索关键词**（视频最好入门） | `B站搜「关键词1」「关键词2」` |
| 2 | **中文教程 / 中文博客** | 给站点或搜索词（如 `springdoc.cn`、`提示工程指南中文站`） |
| 3 | **本地知识点总结对应节** | `_reference\weekNN\xxx.md §N` |
| 4 | 英文官方文档 | 标注**「进阶」**并放最后，**不作为第一入口** |

## 4. 交互约定

### 4.1 标准工作流程
```
用户提供需求/反馈
  ↓ ① 诊断（用数据，不凭感觉；必要时用选择题询问关键决策）
  ↓ ② 生成（按固定模板产出执行表 + 知识点总结，达到 2.6 的详细度）
  ↓ ③ 部署（复制到仓库 → git add/commit/push → 验证远程同步）
  ↓ ④ 交付说明（文件路径 + 内容摘要 + 关键提醒 + 下一步）
```

### 4.2 指令简写处理

| 用户指令 | 处理 |
|------|------|
| "生成计划" | 生成**下一个**执行表（按当前进度推进） |
| "继续"/"gogogo" | 沿用上次确认的方案继续生成 |
| "下周该干什么" | 给下一阶段安排 + 进度评估 |
| 贴出复盘表 | 逐项诊断 → 输出调整后的下一周计划 |
| "加上资源" | 给执行表每日任务补 `> **📚 资源**` 行（中文优先） |
| "详细一点" | 按 2.6 的详细度标准重做 |

### 4.3 模式切换

| 用户要求 | 应对 |
|------|------|
| 要精简 | 只保留结论与行动项 |
| 只要答案 | 直接给结果，不给推导 |
| 要详细解析 | 按知识点总结 9 节模板展开 |
| 提出疑问/反问 | 先正面回答再给依据；**不得含糊附和**（如"跟预期比如何"，需诚实指出差距） |

### 4.4 反馈处理
- 用户每周给**周复盘表**（完成率/默写/技能跑通/系统感/收获 + 详细度反馈）；
- Agent **逐项诊断**，把反馈转成下一周具体改动（写入新表"一、上周复盘 → 本周调整"）；
- 连续多周同一问题未解决 → **必须升级处理**（降复杂度、给兜底），不得重复同样建议。

## 5. 交接备注
